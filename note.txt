# TASK 5 — DOPILOT: Complete Reliability Audit, Performance Optimization, Security Hardening & Deployment Preparation

## Objective

Continue working in the existing Dopilot monorepo.

Tasks 1–4 are complete. Dopilot currently supports:

- Groq-powered autonomous AI agent
- Browser navigation and tab management
- DOM-based browser interactions
- Screenshot-based Vision AI
- Voice commands and speech-to-text
- Text-to-speech
- MCP browser tools
- Chrome and Brave extensions
- Website and extension communication
- User-provided Groq API keys

The application has been tested manually with a real Groq API key.

**Current user feedback:** Dopilot works well overall, but occasionally freezes, responds slowly, executes incorrect actions, or produces incorrect AI outputs.

Your primary responsibility is to identify and fix these problems, then prepare the application for eventual public deployment.

Do not assume the existing implementations are correct merely because automated tests pass.

## 1. Full Project Audit

Inspect the entire monorepo.

Review:

- Frontend and extension communication
- Agent execution loop
- Groq inference integration
- Browser tools and DOM interaction
- Vision implementation
- Voice implementation
- MCP architecture
- Extension service worker
- State management
- Error handling
- Security and permissions
- Performance bottlenecks

Identify actual root causes through code inspection, tests, and runtime evidence.

Fix identified defects instead of adding superficial workarounds.

Preserve all working functionality.

## 2. Fix Agent Freezing and Stuck Tasks

Investigate why Dopilot occasionally gets stuck while executing instructions.

Pay special attention to:

- Hanging Groq API requests
- Unresolved promises
- Message bridge timeouts
- Service-worker suspension
- Race conditions
- Navigation delays
- Stale element references
- DOM observation failures
- Repeated tool calls
- Infinite reasoning loops
- Pending approval prompts
- Multiple simultaneous task executions

Implement:

- Per-operation timeouts
- AbortController-based cancellation
- Reliable task-state transitions
- Controlled retries with exponential backoff
- Detection of repeated actions without progress
- Safe handling of interrupted execution
- Automatic recovery from recoverable failures
- Clear failure messages for unrecoverable situations

Do not blindly retry non-idempotent actions, such as clicking Submit or sending a message.

The Stop button must reliably cancel pending operations and prevent subsequent browser actions.

Ensure no task remains indefinitely in Thinking, Observing, or Executing.

## 3. Improve AI Reasoning and Tool Selection

Audit the agent's system prompts, tool schemas, reasoning flow, and model selection.

Improve its ability to:

- Interpret natural-language instructions correctly
- Understand the user's intended tab
- Select appropriate browser tools
- Execute actions in the correct order
- Avoid unnecessary tool calls
- Recover when an action fails
- Understand when a task is completed
- Avoid reporting success before verification
- Ask for clarification when an instruction is genuinely ambiguous

Example:

"Open a new tab and open YouTube."

Expected behavior:

1. Create exactly one new tab.
2. Navigate that same tab to YouTube.
3. Verify the navigation succeeded.
4. Report completion.

Do not open multiple unnecessary tabs or repeatedly navigate to the same website.

Improve contextual references such as "this tab", "previous tab", and "the button on my screen".

Review whether model-generated tool calls conform to Groq's actual API behavior.

## 4. Groq Model Optimization

Review the latest available Groq integration and configured models.

Implement a reliable capability-aware model selection system:

- Text and tool calling
- Vision
- Speech-to-text

Do not assume every model supports the same capabilities.

Requirements:

- Validate selected model capabilities before use.
- Handle retired or unavailable models.
- Distinguish model failures from application bugs.
- Use the user's selected model when supported.
- Provide meaningful fallbacks that respect user preferences.
- Never silently downgrade to a model that cannot perform the requested task.
- Avoid unnecessary model discovery requests.
- Cache model metadata appropriately.
- Respect free-tier rate limits.

Optimize prompts and tool definitions without sacrificing tool accuracy.

Do not add paid APIs or subscriptions.

## 5. Performance Optimization

Profile real execution paths.

Measure:

- Time to first agent response
- Groq API latency
- DOM observation time
- Browser command execution time
- Screenshot processing time
- End-to-end task completion time
- Tool-call count
- Estimated token usage

Optimize:

- Repeated webpage observations
- Large DOM payloads
- Conversation history size
- Screenshot compression
- Vision invocation frequency
- Redundant model requests
- Browser messaging overhead
- Frontend rerenders
- Side-panel responsiveness

Prefer deterministic execution for simple requests.

For example, basic commands such as opening a tab should not require Groq inference when they can be executed reliably without AI.

Avoid excessive parallel operations that might cause rate limits.

Add lightweight diagnostic timings without exposing private page content, API keys, or sensitive URLs.

## 6. Voice Reliability

Investigate the complete voice-command pipeline.

Fix potential problems involving:

- Microphone start/stop handling
- Speech recognition errors
- Empty transcriptions
- Recording delays
- Multiple recordings
- Duplicate command submissions
- Audio upload failures
- Brave compatibility
- Groq speech-to-text failures
- Cancellation during recording

Improve transcription handling and UI feedback.

Keep push-to-talk as the default.

Do not introduce always-on background recording.

Maintain the text-input fallback.

## 7. Vision Reliability

Audit the screenshot and visual-targeting implementations.

Improve:

- Screenshot capture reliability
- Screenshot freshness verification
- Image preprocessing
- Visual target identification
- Matching visual targets to DOM elements
- Coordinate scaling
- Scrolling and viewport changes
- Dynamic webpages
- Misidentified elements

Prefer verified DOM interactions over coordinate clicks.

If a visual target cannot be identified confidently, do not guess.

Do not perform repeated screenshots without a justified reason.

Ensure screenshot capture permission handling remains secure.

Test against real-world websites.

Focus on:

- YouTube

Test:

- Opening tabs

- Typing
- Searching
- Scrolling
- Dropdowns
- Dynamic page changes
- Multiple sequential instructions
- Handling inaccessible elements

Ensure browser actions affect the intended tab.

Prevent accidental navigation away from the Dopilot website or settings pages.

Improve behavior when users manually change tabs during execution.

Handle unsupported pages and iframe limitations explicitly rather than pretending an action succeeded.

## 9. MCP Integration Audit

Inspect the existing MCP architecture.

Verify that:

- MCP tools are registered correctly.
- Tool arguments are validated.
- Browser permissions are enforced.
- User approvals cannot be bypassed.
- MCP and agent tools share the same execution logic.
- Tool failures return structured errors.
- Local MCP transport works reliably.
- Unauthorized remote connections are impossible.

Preserve the extension's ability to run without a separate Node.js MCP server.

Do not introduce unnecessary MCP servers merely to increase the number of tools.

## 10. Security and Privacy Audit

Review the application as a publicly distributable AI browser extension.

Focus on:

- Groq API key storage
- Extension messaging
- Website origin verification
- Optional browser permissions
- Screenshot privacy
- Microphone privacy
- Prompt injection
- Sensitive webpages
- Browser tab isolation
- Approval bypasses
- Malicious page content
- Unsafe URL handling
- Accidental disclosure of page information

Important requirements:

- Never expose Groq API keys to the website or backend.
- Never log secret values.
- Never allow webpage content to issue privileged instructions.
- Preserve approval requirements for sensitive actions.
- Prevent unauthorized screenshots.
- Keep the browser's internal pages inaccessible.
- Preserve protections against automatic graded-quiz submission and CAPTCHA solving.

Investigate whether the current `<all_urls>` permission can be reduced or avoided using `activeTab` and user-granted access.

Prefer narrower permissions where technically possible.

Do not weaken security merely to improve automation success rates.

- Accessible Stop button
- Understandable error messages
- Easy retry controls
- Groq connection information

Make long-running tasks understandable to users without excessive notifications or animations.

Maintain consistent styling between website and extension.

## 12. Deployment Preparation

Prepare Dopilot for public use.

Target architecture:

- Website: Vercel
- Backend: Render, if genuinely necessary
- Extension: Chrome and Brave through Chromium extension distribution
- AI: Users' own Groq API keys
- MCP: Browser-side adapter with an optional local development server

Tasks:

1. Audit production environment variables.
2. Prepare secure production builds.
3. Confirm the website works over HTTPS.
4. Define production website-to-extension communication.
5. Investigate extension ID handling and distribution.
6. Ensure development-only origins are not allowed in production.
7. Prepare configuration for production domains.
8. Remove development-only behaviors from production builds.
9. Review Chrome Web Store compatibility.
10. Prepare installation and setup instructions.
11. Verify production builds do not expose credentials.
12. Determine whether the backend is necessary for the current product.

Important: The current extension ID is pinned for local development. Design a correct production strategy without breaking existing local installations.

Do not assume a browser extension has the same ID when installed unpacked versus distributed through a browser store.

Avoid reliance on manually copied extension IDs or unrestricted cross-origin messaging.

Assess whether backend hosting can be eliminated for the initial release, since agent execution and Groq requests already occur inside the extension.

If backend hosting is unnecessary, retain the backend source but keep production deployment independent of it.

**Do not deploy yet. Do not purchase domains, hosting, or services.**
